# 阶段一契约与验收

版本：1.0.0

日期：2026-10-30

范围：一个用户和一个 DeepSeek 角色的独立伴随记忆服务

本阶段把 [完整开发方案](../../docs/独立伴随记忆服务开发方案.md) 落为可以检查的数据与接口契约，供后续存储、任务、MCP 和模型整理实现共同使用。产品语义以完整方案为准；本文件固定第一阶段新增的字段、格式与校验细节。

## 2 契约版本与序列化

所有业务请求、记忆快照、候选补丁、工具结果和归档清单携带 `contract_version: "1.0.0"`。未知版本拒绝，不静默降级。包版本 `0.1.0` 描述代码交付，不替代契约版本。

ID 是长度 1 至 128 的稳定 ASCII 标识，只接受字母、数字、点、下划线、冒号与连字符，首字符须为字母或数字。来源原 ID 不符合时由适配器建立稳定映射并保留原值，不把文件路径当 ID。

版本、序号、代次都使用非负或正的安全整数，不能用浮点数、时间戳或随机值替代。新建记忆为版本 1；已有记录每次修订增长 1；`expected_version=0` 只用于声明新建。

字符串及证据位置按 Unicode 码点计数，使用 `[...text].length` 与对应切片；不是 UTF-16 单元数、字节数或 token 数。组合音标和 ZWJ 序列可能由多个码点组成，不按视觉字形计数。原话不自动 trim、改人称或 Unicode 归一化。

归档原件和内容的哈希是原始字节的 SHA-256，小写 64 位十六进制。请求幂等哈希使用 `sorted-keys-json-v1`：纯 JSON 对象的键按 JavaScript UTF-16 字符串顺序排序，数组顺序不变，使用 JSON 数字和字符串序列化，不增加空白。它不是 RFC 8785 兼容性声明。undefined、非有限数、非纯 JSON 对象、稀疏数组与循环引用被拒绝。

## 3 时间 人物与依据

### 3.1 时间结构

`TimeRange` 按 `precision` 区分 `unknown`、`year`、`month`、`day`、`instant`。

- unknown 的 start、end 必须为 null，basis 为 unknown，时间证据为空。
- 其他精度分别使用 `YYYY`、`YYYY-MM`、合法 `YYYY-MM-DD` 或带时区的 ISO 时间；瞬时时间必须含秒，小数秒最多三位，与 JavaScript 毫秒比较精度一致。
- 已知时间须有 basis 和证据 ID；end 可为空，非空时不能早于 start。
- 不接受公历年零，不用记录时间补事件时间，不把不明年份推成确定年份。
- 事件 occurred、情绪 felt_time、消息 captured_at、记忆 created_at / updated_at 各自独立。

不把部分日期转成虚构的某天中午。数据库保存结构与精度，检索时再按用户时区解释日期范围。

### 3.2 人物与范围

人物 kind 为 `user / character / historical_ai / third_party / unknown`。一个 companion 当前只绑定一个 user 与一个 character；历史 AI 和第三方可以有多项。相同名字不自动等于相同人物。

`scope` 必填，kind 为 episode、conversation 或 companion，id 必须指向同一 companion 内对应类型对象。经历中的解释不能直接以 companion 范围成为全局规则，也不能指向无关经历。

### 3.3 证据

证据固定引用消息的会话、分支、回合、序号、消息 ID 与版本，或引用来源条目的 source_id、external_id 和 content_hash。保存 speaker_actor_id、原样 quote 与半开码点范围 `[start,end)`。

校验时对照可信输入快照，检查当前有效消息链、归属、角色、文本位置和逐字一致性。传入的 role、actor 或 quote 本身不产生可信身份；服务端构造 ValidationContext。注入的回忆和系统提示不作为新用户证据。

`legacy_summary` 不升级为逐字用户陈述；经导入验证的人类原始对话可作为直接用户证据。助手推测不能通过改一个 basis 字段变成用户确认。上下文推断也要有用户线索，不能只有助手自己提出的感受。

Schema 和守卫能检查来源与版本，不能自动证明一句自然语言的真实情绪、引文指代或长期适用性。样本中的人工期望为后续模型评估提供标准，不是假装已经实现了语义分类器。

## 4 三类可版本化记录

`memory_records` 是共同父记录，分为：

| kind | 用途 | 作用域 |
| --- | --- | --- |
| episode | 用户经历与动态理解 | 经历自身，并可关联具体会话 |
| communication_pattern | 明确的长期偏好或有条件观察模式 | companion |
| response_need | 本次希望被倾听等临时需要 | episode 或 conversation |

本次需要单独版本化，便于会话级作用域、撤回和接口幂等；经历中也可保存带证据的 response_need 解释。二者必须引用同一依据，由后续事务服务维护一致，不形成两个互相矛盾的永久规则。

共同字段包括 id、companion_id、version、suppression_generation、内容状态、发布状态、记录时间与证据引用。主设定没有可写正文，所有业务对象拒绝未声明字段。

经历保存概要、详情、人物、发生时间、事件进展、冷热层级、最近有效提及和解释列表。解释区分 emotion、intent、response_need；记录主体、依据、状态、时间、表达回合和被替代关系。

未知人物默认保持 staged。corrected 解释保留在修订或详情历史中，并指向有效替代解释，不能作为默认召回中的当前理解返回。

长期 observed_pattern 至少要有两个独立上下文、有适用条件并检查反例。这是 v1 的最低结构门槛，不代表两个样本就足以判断真实规律；具体是否形成模式由后续评估决定。重复观察不能自行成为 user_confirmed。explicit_preference 要有支持长期适用的用户陈述，不能把单次需要仅换一个字段名就提升为永久偏好。

## 5 六个工具的参数与结果

权威结构由 [生成的 Schema](../contracts/schema-bundle.json) 的 `$defs` 提供：每个工具分别有 `<name>_input` 与 `<name>_output`。导出文件的 `x-tools` 还记录调用能力和默认受众；注解不替代权限控制。

| 工具 | 调用能力 | 契约重点 |
| --- | --- | --- |
| recall_context | read | 绑定会话与链版本；近期文本须与真实消息一致；冷目录可参与后续检索 |
| observe_turn | observe，可信宿主 | 接收实际可见消息；保存成功不代表理解完成 |
| get_episode | read | 只能取绑定范围内的经历，详情有预算 |
| correct_memory | user_edit，宿主确认实际用户依据 | targets 列出全部基础版本，mutations 与 links 整组提交 |
| set_memory_preference | user_edit | create 版本为 0；update 必须有 ID、基础版本和撤回水位；明确局部或长期作用域 |
| retract_memory | user_edit | 版本与撤回水位增长，停止召回，不宣称物理擦除 |

普通模型默认仅暴露 read 能力。宿主接收、用户纠正和本地管理凭据分别控制，避免把任意模型文本当成用户原话。后台候选通过内部 candidate 能力校验，不注册为模型可任意调用的写库工具。

### 5.1 接收回合

observe_turn 包含 contract_version、request_id、conversation_id、branch_id、chain_revision、turn_id、sequence 和 messages。

messages 中每项单独提供 message_id、revision、position、role、text、status、captured_at。position 从 0 连续递增，用户消息在助手回复之前，原始用户输入为 complete；中断的助手内容可以是 interrupted。没有可见内容的已完成消息被拒绝。

末尾追加回合不增加 chain_revision。修改有效链中的消息或分支拓扑才产生新链版本。接收可以乱序；已接收水位与已处理水位均只向连续位置推进，缺口或失败不能跳过。

成功接收的 data 为 receipt=accepted、processing_status、duplicate、job_ids、accepted_through、processed_through。水位的会话、分支和链版本一致；processed_through 不超过 accepted_through。某回合仍高于已处理水位时，不能声称它已 processed。

### 5.2 纠正与候选补丁

纠正 targets 的每项包含 memory_id、expected_version 和 suppression_generation。每个 revise mutation 必须对应一个目标，产生下一版本，保持记录身份、种类和创建时间；每个目标恰有一个 mutation。

create mutation 使用 temporary_id，record.id 必须相同，版本为 1、撤回水位为 0，不能与已有记录碰撞。最终 ID 由服务分配，并返回 temporary_id 到新 ID 的映射。split / merge 的关系和全部既有目标必须同事务提交；发生冲突不返回部分成功。

后台候选额外包含 job_id、输入消息清单、input_watermark、source_guards、新证据和修订理由。候选输入必须属于当前有效链，并包含其声明水位的末尾回合。已有来源证据即使不重新提交，也须有跨内容哈希的屏蔽水位守卫。

已撤回记录不能通过普通候选恢复。真实恢复若未来需要，应单独设计有明确授权的操作，不复用自动更新。

### 5.3 统一业务结果

协议外壳由后续 MCP SDK 承担；本阶段固定业务包裹：

```json
{
  "contract_version": "1.0.0",
  "outcome": {
    "status": "error",
    "error": {
      "code": "VERSION_CONFLICT",
      "message": "记忆已有更新，请使用最新版本。",
      "retryable": true,
      "paths": ["targets"]
    }
  }
}
```

成功时 outcome 为 `{ "status": "ok", "data": ... }`。两种结果互斥，禁止一边报错一边携带成功 data。

错误码固定为 VALIDATION_ERROR、FORBIDDEN、NOT_FOUND、VERSION_CONFLICT、IDEMPOTENCY_CONFLICT、STALE_INPUT、ARCHIVE_UNAVAILABLE、MODEL_UNAVAILABLE、BUDGET_EXCEEDED。公开错误不泄露他人资料、原文或密钥。

纠正成功要返回整个目标集合的新版本，不能遗漏任何既有目标。撤回结果 physical_deletion 固定 false。完整数据未落盘前，后续服务不能生成 committed=true 的结果。

### 5.4 预算

recall_context 的 max_items 为 1 至 12，max_chars 为 1 至 6000；近期上下文最多 6 条，合计最多 8000 码点。get_episode 也有最大 6000 码点的请求预算。所有业务结果还有 128 KiB UTF-8 序列化硬上限。

召回 max_chars 检查 `JSON.stringify(items)` 的码点数，计入资料项的来源、证据等元信息；详情预算检查序列化 data。它比只限制正文更保守，避免复杂证据绕过预算。字节上限另行计算，不等于码点或 token 数。

返回服务必须生成符合预算的投影；不能放入完整超长条目后再声称已裁剪。若没有任何资料能放入，可返回空 items、truncated=true 和 budget_truncated，不能突破上限。实际选条、裁剪和 token 预算属于后续召回实现。

## 6 数据库迁移草案

[001-initial.sql](../contracts/database/001-initial.sql) 是可执行的结构草案，测试只在 `:memory:` 中应用。阶段二仍需实现迁移版本表、运行连接、事务服务、忙等待、WAL、重启恢复与备份，不应直接把测试 helper 当作服务。

核心设计决定：

1. 组合外键使用 companion_id 与记录 ID，避免有效 ID 跨角色关联。
2. 回合顺序、逻辑消息位置与不可变消息版本分别保存。branch_messages 选择当前有效版本，不覆盖历史正文。
3. source_items 保存跨哈希的来源身份与屏蔽状态，source_records 保存内容版本；导入文件搬家不产生新身份。
4. memory_records 指向确定的 memory_revisions。相互引用使用延迟外键，建立或修订必须同一事务完成。
5. 事件、长期模式和临时需要分别有子表；临时 scope 拆为有类型外键的列，不依赖无法验证的多态字符串。
6. content_objects 保存不可变哈希和长度，object_locations 保存可迁移的物理位置。这样归档不必改写原话、修订或证据的身份。
7. 归档未 ready 时不能把唯一位置切过去；已发布成员不可变。物理文件验证仍由归档服务承担。
8. 证据、来源版本、消息版本和记忆快照追加保存。普通更新不能解除撤回或降低屏蔽水位。

SQL 不证明用户情绪、不计算 SHA-256、不验证自然语言长期适用性，也不能证明某文件已经刷盘。它与服务语义守卫一起构成契约，不应只跑 DDL 就宣称所有系统不变量已成立。

角色主设定只保存 persona_reference 和可选摘要，不包含后台可编辑的主性格正文。

## 7 归档格式草案

v1 草案是一个受服务管理的不可变目录对象：

```text
objects/<archive_id>/
├─ manifest.json
└─ payload.zst
```

payload.zst 按成员清单顺序连接独立 zstd 帧。每个成员用 offset_bytes 和 compressed_bytes 定位，不存可逃出对象目录的任意成员路径。payload_file 固定为 payload.zst。

manifest.json 是 canonical UTF-8 JSON，无 BOM。数据库保存其实际字节的 SHA-256，清单不自包含自己的哈希。清单包含整个 payload 的哈希、成员列表、格式与 Schema 版本；每个成员分别保存压缩帧哈希和解压原文哈希。

所有 offset 和 length 都是字节；成员必须连续、不重叠、不重复，成员字节总和与包总和一致。memory_revision 成员必须指定 memory_id 与 memory_version；非记忆载荷可为空，但两者必须同时有值或同时为空。

建议初始硬限制为成员最多 256 个、单成员解压最多 4 MiB、总解压最多 32 MiB、压缩载荷最多 40 MiB、清单最多 1 MiB。大原件超过单成员限制时保留在不可变导入快照，不擅自丢弃或超限归档；后续若需要分块，升级格式并记录可重建的块清单。

阶段七还需核验 zstd 实现、校验实际帧、限制解压流输出和耗时、完成目录发布、刷盘恢复、备份及重新打包。本阶段 manifest 校验只验证元数据，示例哈希不代表已有真实压缩包。

cold 只是一种物理层级。成为 cold 之前，必须确认输入版本仍有效、没有待完成修订、验证成功、对象已发布、目录已提交且保有可恢复持久副本。retracted 记录不能因解压或缓存命中变回 active。

### 7.1 状态转换边界

| 维度 | 允许的转换与前置条件 |
| --- | --- |
| 内容 | active 与 disputed 可在有依据修订中变化，也可进入 retracted；retracted 在普通流程中终止 |
| 理解 | tentative、supported 可随证据变化；user_confirmed 需要用户直接证据；corrected 必须有替代解释且不能自行复活 |
| 用户确认 | 自动推断不能把 user_confirmed 降为另一种现行推断；用户纠正形成 corrected 与新的解释 |
| 存储 | hot 到 warm 要满足闲置和无待处理修订；warm 到 cold 还需事件结束及完整归档发布守卫 |
| 唤醒 | 解压读取可以保持 cold 并建立缓存；只有用户有效再次谈起才进入 hot，不因后台读取变热 |
| 任务 | queued 到 running，失败后有界 retry_wait；completed、stale、failed、cancelled 为终态，重算使用新的任务身份 |

这些是纯契约谓词，后续服务必须在事务和可信上下文中执行；布尔 guard 不能由模型自行声明为 true 后绕过验证。

## 8 样本和测试边界

[conversations.generated.json](../fixtures/conversations.generated.json) 包含九组人工合成样本和逐步期望：渐进倾诉、情绪真实变化、明确纠正、历史情绪与现在变化、第三方引文、未知时间与人物、表达的条件与反例、Unicode 证据以及明确长期偏好。

每个检查点只使用该水位之前的有效输入，不允许用最后一轮的情绪倒填第一轮期望。验证样本中的 expected_records 是人工标准结果，不是自动读取原话生成的模型输出；后续抽取器需要额外对照这些标准评估。

[dsh-import.generated.json](../fixtures/dsh-import.generated.json) 保留自定义字段、已有改写、人称不明、已取代关系与原 AI 身份。它是导入设计样本，未声称已经实现只读导入或真实数据恢复。

目前检查分为四层：

| 层 | 检查什么 | 不代表什么 |
| --- | --- | --- |
| 类型与结构 | TypeScript、Zod、生成 Schema 和拒绝未知字段 | 自然语言理解正确 |
| 语义守卫 | 证据引用、版本、来源、范围、水位与预算关系 | 数据库已事务性落盘 |
| SQL 草案 | 外键、唯一、不可变、延迟引用、回滚和位置迁移约束 | 生产迁移器或文件系统发布已完成 |
| 人工期望样本 | 合成对话与阶段期望一致、没有未来证据泄漏 | DeepSeek 已通过抽取效果评估 |

SQL 的两个 companion 只用于负例隔离测试，不改变首版一个用户和一个角色的范围。

## 9 运行与后续交接

使用 Node.js 24.19.0，进入 standalone 后执行 npm ci --ignore-scripts 与 npm run check。不需要 DSH、DeepSeek、网络服务或私人记忆；首次安装依赖需要访问包仓库。

schema-bundle.json 与两个 generated 样本由 npm run schemas:write 重建。npm run schemas:check 检查漂移，防止代码改了而导出契约未更新。不能仅修改生成 JSON 来绕过源 Schema。

阶段二接手时：

1. 使用同一契约版本与错误语义，不自行省略版本、scope 或来源守卫。
2. 将 DDL 草案变成有编号和恢复策略的实际迁移；所有迁移先在副本和临时目录验证。
3. 实现可信 ValidationContext 的读取与原子提交，不能把客户端传入的角色和证据直接放进可信上下文。
4. 加入幂等请求持久化、比较版本更新、任务租约和运行数据目录。
5. 对本阶段已有用例保持回归，再增加真实事务、文件故障和重启测试。
6. 不提前连接未知人物仓库，不读取原 DSH 记忆，不注册真实 MCP 或启动后台模型任务。
